# 跨平台交付：一套歌词、两套包装，以及模型怎么选

> **什么时候读这一章**：用户说"用哪个模型好""这个模型会把括号念出来""风格描述最多 800 字""文件里只有提示词没有歌词"，或者同一首歌要在不同平台各出一版。

---

## 一、为什么要"双包装"：括号在不同模型里是两种东西

同一份带圆括号说明的歌词，在不同模型里的命运完全不同：

| 模型行为 | 后果 | 交付方式 |
|---|---|---|
| 把 `（能量 9 · 四踩全开）` 当**注释/提示**读 | 正常，且能吃到能量/配器指令 | **括号版**（默认） |
| 把括号内容当**歌词**唱出来 | 成品里会有"能量九"这种念白，整首废掉 | **零括号版** |

**结论：同一份歌词要准备两套包装。** 交付时先问一句"你用哪个平台"，或者直接给两版，标清哪个粘哪个框。

---

## 二、零括号版的五条规则（以 MiniMax 实测为例）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **结构标签独占一行** | `[Verse 1]` 单独一行，标签后面不能跟任何说明（`[Verse 1 – 领唱]` 会被念出来） |
| 2 | **段落说明全部搬进"音乐描述"框** | 演唱分工、能量、配器在歌词里无处安放，只能写进 style prompt |
| 3 | **按段落顺序讲一遍** | 因为标签里不能带信息，"前奏→主歌1→预副歌→副歌→间奏→主歌2…"必须按顺序叙述，和歌词顺序对齐 |
| 4 | **用 plain 标签** | `[Chorus]` 安全；`[Chorus - anthemic]` 这类加修饰的写法在部分平台**未文档化**，可能被当歌词 |
| 5 | **不要留空段** | post-chorus 若写"纯器乐、人声只留气"，模型会乱塞词或跳段；改为真实 chant `Hey! Hey!` ×2 行（这是歌词，不是提示） |

**排错表**

| 症状 | 原因 | 修法 |
|---|---|---|
| 唱出"能量九""四踩全开" | 圆括号进了歌词框 | 改零括号版 |
| 报"歌词格式错误" | `[Intro]` 后面空着 | 删掉那一行 |
| 生成结果和描述完全不符 | 两个框填反了 | 风格描述只写声音，歌词只写词＋标签 |
| 段落顺序乱 | 标签和歌词挤在同一行 | 一行一个标签 |

## 三、模型选型方法论：卡片文案 ≠ 能力边界

**最容易犯的错**：把平台模型卡片上那四行简介当成能力边界。那是营销文案，只说了它擅长什么，从不说它**不支持**什么。

### 四查（选型必做）

| # | 查什么 | 为什么致命 |
|---|---|---|
| 1 | **收不收负面提示词**（negative / style_negative） | 我们的提示词常常一半是禁令（不要民谣/不要木吉他/不要抒情）。收不到禁令，模型会退回它最常见的那个曲风——等于白写 |
| 2 | **支不支持"歌词"与"指令"分栏传参** | 不支持分栏的模型，强行分开反而导致生成错乱，与双栏工作流直接冲突 |
| 3 | **第三方测评的硬数据** | 中文音素错误率、音乐性/自然度评分。**人声好听 ≠ 咬字准确**，这两件事经常反向 |
| 4 | **平台上的版本号 vs 旗舰版本号** | 平台上常是旧版（如 v4.1a），旗舰可能已到 v4.7，能力差距很大 |

### 真实翻车案例（三处被查证推翻）

| 看卡片得出的结论 | 查证后 |
|---|---|
| "强调提示词遵循精确"→ 并列首选 | 该系列官方 API 文档写明**不支持负面提示词**；而这份提示词一半是禁令 → 必须改写成正向封闭清单才能用 |
| "主打续写/仿写"→ 只能做续写，不适合整首 | 它其实是完整写歌产品，主打记忆点 Hook 与编曲层次；"续写"只是其中一个功能 |
| "人声情绪丰富、演唱功力"→ 人声首选 | 第三方实测中文音素错误率约 24.5%（对比模型 8.4%），SongEval 四项最低 → **只作人声参考，不作咬字保证** |

### 选型的通用原则

1. **提示词设计密度越高的歌，越要选"提示词遵循精确"的模型**——设计全在提示词里，遵循不准就全丢；
2. **想要人声语气（撒娇、自嘲、半说半唱），选"演唱功力"强的模型**，但要接受咬字风险，并优先做咬字自检；
3. **公开资料查不到的模型，只能当"赌一把"，不能写进推荐**——如实说明置信度，不要把"可能不错"说成"应该不错"；
4. **版本与价格会变**，选型结论要带日期，用户下次来问要重新核。

## 四、没有 negative 字段怎么办：用"封闭清单"代替禁令

禁令型写法（需要模型支持负向提示词）：

> 不要木吉他主导、不要民谣、不要抒情、不要慢、不要 lo-fi。

**改成正向封闭清单**（任何模型都能执行）：

> 编曲全部由这五件构成：合成器 pluck、电子鼓、synth bass、电钢、拍手。人声之外不出现原声吉他。

要点：

1. **给出"全部由……构成"的封闭集合**，模型只能在集合内选，自然就排除了集合外的东西；
2. **全篇最多留一个否定词**，其余全部改成正向陈述；
3. 篇幅会变长，但如果平台支持长提示词（如 1000 字），这是唯一可靠的办法。

## 五、风格提示词字数纪律

| 场景 | 上限 | 出处 |
|---|---|---|
| 纯音乐 | **≤500 字符**（含标点空格） | `06-instrumental-playbook.md` 第一节 |
| 带人声（平台默认） | ≤1000 字符 | `11-miaoxiang-prompt-rules.md` 第三节 |
| 用户指定（如"800 字以内"） | **按用户数字执行** | 用户要求优先于平台舒适值 |

### 压缩优先级（从上到下砍）

1. **删解释与理由**（"这样做的原因是……""因为……所以……"）——一句不留；
2. **删重复**（同一件事在两处说了）；
3. **缩词不缩意**（"第一遍/第二遍/第三遍"→"首遍/二遍/三遍"；"旋律性格"→"旋律"；"音域只有五度"→"五度内"）；
4. **合并同类**（三条并列的情绪点合成一条）；
5. **只删修饰语**（"孤零零地""非常""尽量"）。

### 三条铁律

1. **指令一条不删**：能被执行的动作（进什么乐器、第几小节、多响）全部保留；
2. **点名引文全留**：`"掀开"——音往上跳，不拖` 这类点名句是提示词里唯一真正起作用的部分；
3. **交付前用脚本核字数**，不要目测：

```python
import re
block = open('style.txt').read()
print(len(re.sub(r'\s', '', block)))   # 去空白字符数
```

**标题上直接标字数**（如「风格提示词 794 字」），用户一眼能核对。

## 六、交付前三问

1. **用户用哪个平台？** 不确定就给两版（括号版 / 零括号版），并标清哪个粘风格栏、哪个粘歌词框。
2. **这份文件里"能直接复制"的块齐了吗？** ①风格提示词 ②完整歌词，两个都要有——**只写技法、忘了放歌词框，是最常见的交付事故**。
3. **字数核过了吗？** 纯音乐 500／带人声 1000 或用户指定值，脚本核完再交付。
